## 5. REST API Specs (Лабораторная работа №2)

Базовый URL: `http://localhost:8080/api/v1`. Формат данных - JSON.
Аутентификация - JWT (`Authorization: Bearer <token>`). Полная спецификация - в файле [`openapi.yaml`](./openapi.yaml).

| Метод | URI | Описание | Доступ (роль) | Ожидаемый код |
|-------|-----|----------|---------------|---------------|
| GET | /api/v1/health | Проверка работоспособности сервиса | Все | 200 OK |
| POST | /api/v1/auth/register | Регистрация водителя | Все | 201 Created |

### Типовые коды ошибок

| Код | Когда возвращается |
|-----|--------------------|
| 400 Bad Request | Невалидные входные данные |
| 401 Unauthorized | Токен отсутствует или недействителен |
| 403 Forbidden | Роль не позволяет выполнить действие (например, водитель пытается добавить авто) |
| 404 Not Found | Ресурс не найден |
| 409 Conflict | Авто уже занято, email уже зарегистрирован, недопустимый переход статуса |
| 500 Internal Server Error | Необработанная ошибка сервера |

Все ошибки возвращаются в единой схеме `ErrorResponse`: `{ "code", "message", "timestamp" }`.

### Соответствие Use Cases и эндпоинтов

| Use Case | Эндпоинт |
|----------|----------|
| Водитель регистрируется и входит | POST /auth/register, POST /auth/login |
| Водитель ищет свободное авто | GET /cars?status=Available |
| Водитель бронирует авто | POST /bookings |
| Водитель начинает поездку | PATCH /bookings/{id}/status (ACTIVE) |
| Водитель завершает поездку, расчёт стоимости | PATCH /bookings/{id}/status (COMPLETED) |
| Водитель отменяет бронь | PATCH /bookings/{id}/status (CANCELLED) |
| Оператор управляет автопарком | POST/PUT/DELETE /cars, PATCH /cars/{id}/status |
| Оператор настраивает тарифы | POST /tariffs |
| Просмотр финансовых операций | GET /transactions |

### Проектные решения

- Отмена и завершение брони - через `PATCH .../status`, а не `DELETE`: запись о брони и связанные транзакции должны сохраняться для учёта.
- Бизнес-действия выражены сменой статуса подресурса, а не глаголами в URI (`/bookings/{id}/cancel` не используется).
- Статусы авто соответствуют справочнику `car_statuses` из ER-диаграммы (Available, Rented, Maintenance).
- Список ресурсов поддерживает пагинацию через `limit` и `offset`.

## 6. Ответы на контрольные вопросы (ЛР2)

**1. Query, Path и Request Body - в чём разница и как выбирать?**
- *Path* (`/cars/{id}`) - идентифицирует конкретный ресурс; параметр обязателен и входит в сам адрес.
- *Query* (`?status=Available&limit=10`) - необязательные параметры фильтрации, сортировки, пагинации коллекции; не меняют, *какой* ресурс запрашивается.
- *Request Body* - данные создаваемого или изменяемого ресурса (POST, PUT, PATCH): большие, структурированные, содержащие чувствительные данные (пароль), которые нельзя класть в URL (URL попадает в логи и историю).

Правило: идентификатор - в Path, фильтры - в Query, полезная нагрузка - в Body.

**2. Что такое идемпотентность?**
Метод идемпотентен, если повторный вызов с теми же параметрами оставляет сервер в том же состоянии, что и однократный. GET только читает данные. PUT устанавливает ресурс в заданное состояние - повтор даёт тот же результат. DELETE после первого вызова ресурс уже удалён, повтор не меняет состояние (ответ может быть 404, но состояние системы то же). POST создаёт новый ресурс при каждом вызове: два одинаковых запроса `POST /bookings` создадут две брони, поэтому POST не идемпотентен.

**3. 401 или 403?**
- *401 Unauthorized* - сервер не знает, кто вы: токена нет, он просроченный, подпись неверна, неверный логин или пароль. Решение - пройти аутентификацию.
- *403 Forbidden* - вы известны серверу, но прав на действие нет. Пример: водитель с валидным токеном вызывает `POST /cars`, доступный только оператору; или водитель запрашивает чужую бронь. Повторная аутентификация не поможет.

**4. Зачем `components/schemas` и `$ref`?**
Блок `components` хранит переиспользуемые описания: схемы данных, ответы, параметры, схемы безопасности. `$ref` ссылается на них, что устраняет дублирование (например, `ErrorResponse` и `CarResponse` используются в десятках мест), упрощает сопровождение (правка в одном месте) и делает спецификацию читаемой. Также на схемах основана генерация клиентского кода и автоматическая валидация данных.

**5. PUT и PATCH?**
- *PUT* - полная замена ресурса: клиент передаёт все поля, отсутствующие поля сбрасываются или считаются ошибкой. Идемпотентен. Пример: `PUT /cars/{id}` с полным описанием авто.
- *PATCH* - частичное изменение: передаются только изменяемые поля. Пример: `PATCH /cars/{id}/status` с `{"status": "Maintenance"}` меняет только статус и не требует отправлять VIN, пробег и прочее.

## 7. Структура проекта и слои (Лабораторная работа №3)

Стек: Node.js 22 (ES-модули), без внешних зависимостей. Архитектура - Layered / Clean Architecture.

```text
.
├── cmd/
│   └── app/
│       └── index.js            # Точка входа и Composition Root
├── internal/
│   ├── config/
│   │   └── config.js           # Загрузка конфигурации из .env / окружения
│   ├── controller/             # Transport / HTTP-слой
│   │   ├── http.js             #   sendJson, sendError (формат ErrorResponse)
│   │   ├── router.js           #   маршрутизация
│   │   └── healthController.js #   GET /api/v1/health
│   ├── service/                # Слой бизнес-логики
│   │   └── healthService.js
│   └── repository/             # Слой доступа к данным (появится в след. ЛР)
├── .env.example                # Шаблон переменных окружения
├── .gitignore
├── openapi.yaml                # Спецификация из ЛР2
├── ARCHITECTURE.md             # Архитектура из ЛР1-ЛР3
├── package.json
└── README.md
```

### Поток данных

```text
HTTP Request -> Router -> Controller -> Service -> Repository -> Database (PostgreSQL / Redis)
```

| Слой | Ответственность | Чего НЕ делает |
|------|-----------------|----------------|
| Controller (Transport) | Принимает запрос, парсит параметры, вызывает сервис, формирует HTTP-ответ | Не содержит бизнес-логики, не обращается к БД |
| Service (Domain) | Бизнес-правила и сценарии (расчёт стоимости, холд депозита, смена статуса авто) | Не знает про HTTP, заголовки, JSON-тело |
| Repository (Data) | SQL-запросы, работа с PostgreSQL и Redis | Не содержит бизнес-правил |
| Config | Чтение и валидация переменных окружения | Остальные слои не обращаются к `process.env` напрямую |

Зависимости направлены внутрь: `Controller -> Service -> Repository`. Связывание выполняется в одном месте - `cmd/app/index.js`: зависимости создаются там и передаются в конструкторы (Dependency Injection).

## 8. Ответы на контрольные вопросы (ЛР3)

**1. Почему Service Layer не должен знать о деталях HTTP?**
Бизнес-правила (расчёт стоимости аренды, холд депозита, допустимые переходы статусов) не зависят от способа доставки запроса. Если сервис работает с `req`, заголовками и JSON-телом, его нельзя вызвать из другого источника: gRPC, CLI, очереди сообщений, фонового задания. Такой код сложно тестировать (нужно имитировать HTTP-запрос), а смена транспорта или версии API потребует переписывать логику. Когда сервис принимает и возвращает обычные объекты, его можно тестировать изолированно и переиспользовать.

**2. В чём опасность хранения секретов в исходном коде?**
Код попадает в Git, где история хранится вечно: даже удалённый секрет остаётся в старых коммитах. К репозиторию имеют доступ разработчики, CI/CD, подрядчики, а при публичном репозитории - все в интернете; боты автоматически сканируют GitHub на утечки ключей. Утёкший пароль к БД или JWT-секрет позволяет взломать систему: прочитать данные пользователей, подделывать токены. К тому же один и тот же код должен работать в разных окружениях (dev, test, prod) с разными секретами, а замена секрета в коде требует пересборки и деплоя. Секреты передаются через переменные окружения или менеджеры секретов.

**3. Зачем `.env.example`, если `.env` в `.gitignore`?**
Это шаблон и документация конфигурации. Новый разработчик видит, какие переменные нужны приложению, копирует файл в `.env` и подставляет свои значения. Без шаблона пришлось бы искать названия переменных по коду. В `.env.example` лежат только названия и безопасные значения-заглушки, настоящие секреты не хранятся.

**4. Для чего нужен Health Check?**
Эндпоинт позволяет автоматически понять, что сервис жив и готов принимать трафик. Его используют: оркестраторы (Kubernetes liveness/readiness probes, Docker healthcheck) - чтобы перезапустить упавший контейнер; балансировщики нагрузки - чтобы не отправлять запросы на неработающий экземпляр; системы мониторинга и алертинга; CI/CD - чтобы убедиться, что после деплоя приложение поднялось. В будущем в него добавится проверка подключений к PostgreSQL и Redis.

**5. Что такое инверсия зависимостей?**
Принцип: модули верхнего уровня (бизнес-логика) не должны зависеть от модулей нижнего уровня (БД, HTTP); оба зависят от абстракций. Сервис не создаёт конкретный репозиторий сам, а получает объект с нужным контрактом (интерфейсом), например `findById`, `save`. Конкретную реализацию (PostgreSQL, in-memory для тестов) подставляет Composition Root при сборке приложения. Так контроллер зависит от контракта сервиса, сервис - от контракта репозитория, и любой слой можно заменить или подменить заглушкой при тестировании, не трогая остальные. В проекте это реализовано внедрением зависимостей через конструкторы в `cmd/app/index.js`.
